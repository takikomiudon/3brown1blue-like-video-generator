# 日本語の解説アニメーション — v2.0.0

`$science-explainer` による動画制作は、**説明対象の意味のある動きを必須**とする。
ユーザーが「アニメーション」と追記しなくても適用する。
完成品では、対象の変化を追うことで仕組みを理解できる必要がある。
この条件はスキル本体の契約であり、リンク先を読み飛ばして省略できる追加オプションではない。

## 0. 読み込みと環境

1. この版が **2.0.0** であることを確認し、同梱の [動作の制作・合格条件](references/motion-contract.md) を必ず読む。
2. プロジェクトのAGENTS.md、既存の制作手順・ソース・完成動画を確認する。
   このリポジトリでは [索引](../../../docs/KNOWLEDGE.md) と [制作手順](../../../docs/production-workflow.md)。
3. 新作のManim実装では、[Manim Video Lab](../manim-video/SKILL.md) と
   [Manim CE](../manimce-best-practices/SKILL.md) を読み、アルゴリズムなら
   [論理的な動きの演出](../manim-video/references/algorithm-choreography.md) も読む。
   企画の補助は [Manim Composer](../manim-composer/SKILL.md)。
4. 別プロジェクトへの導入は、SKILL.mdだけでなく **science-explainerフォルダ全体**を持ち込む。
   参照する兄弟スキルと描画環境も用意する。欠けている場合、まず取得・セットアップを試す。
   実行できない場合は、実行・検証が完了した範囲と阻害要因を明示する。
   参照パスはそのスキルの実際の設置先を基準に解決する。

## 1. 出典と、動きの設計

- 対象視聴者と一つの理解を決め、公式資料・既存実装を確認する。
- 制作前に `plan.md` と `motion-plan.json` を書く。
  [動作計画の例](templates/motion-plan.example.json) を参考に、各説明区間について
  **対象id、変化前、動作、変化後、その変化で分かる仕組み、時刻、画面領域**を明記する。
- 説明本体には、対象の移動・変形・分岐・流れ・生成消滅・値に連動する形状変化等を割り当てる。
  各動作について、変化と説明内容の対応を一文で述べる。
- 題材に適した動きを選ぶ。物理なら相互作用、アルゴリズムなら状態遷移、数学なら図形や量の関係、
  制度や歴史なら因果・資源・意思決定の変化を図で追う。対象と表現は毎回題材から決める。
- 読解用の保持では、対象と理由と時間を宣言する。詳細は動作契約を参照。
- 一つの対象・色・座標の意味を場面間で維持する。字幕の領域を主図から分離する。
- テーマに「なぜ」を付けるだけで興味の根拠にしない。人気や品質の向上を未検証で達成済みと呼ばない。

## 2. 必須の動く試作

1. 全編の前に、中心となる仕組みを説明する **5〜10秒の動く試作**を実際にレンダーする。
2. 動画、または同じ対象の途中状態を追える連続フレームで確認する。
   完成時の一枚やコードだけで「動いた」と判断しない。
3. 対象自身の位置・形・状態が変わり、その変化で仕組みが分かることを確認する。
   この条件の合格を確認してから、全編へ進む。
4. 既存のコードを流用しても、試作と最終確認を省略しない。

## 3. 音声と実装

- 現行の描画はManim Community、音声はVOICEVOX。ManimGLのAPIと混在させない。
  Reactで制作する場合は [Remotionスキル](../remotion-best-practices/SKILL.md) と同じ動作契約を使う。
- 台本は `story.json`。発音を確認して音声を先に作り、実測尺を使って動作を配置する。
  重要語の位置には音声クエリのモーラ時刻等を使う。未実施の全語アラインメントを主張しない。
- 計画した対象の状態を補間して実装する。Manimなら `.animate`、Transform、MoveAlongPath、
  ValueTracker/Updater等を意味に応じて使い、実際の描画結果で確認する。
- 動きの原因と結果を同時に示す。矢印・ラベル・数値を対象から離さず、決定論的な状態に結びつける。
- 動作の検査領域は、説明対象が位置する主図とする。
- 既存作品の実装は参考として使う。新作に同じ対象・レイアウトを持ち込む義務はない。
- 音声・素材の利用条件とクレジットを残す。既存作品の映像・キャラクター・声を転載しない。

## 4. 完成判定 — 両方必須

**A. 機械検査**：最終MP4の主図の領域を指定して、同梱の検査を実行する。
主図と補助表示の領域を分ける。コマンドと書式は [動作契約](references/motion-contract.md)。

```bash
python3 /path/to/science-explainer/scripts/audit_motion.py \
  outputs/final.mp4 --plan motion-plan.json --output outputs/motion-audit.json
```

機械検査のみの成功は意味のあるアニメーションの証明ではない。レビュー未実施は終了コード2。

**B. 意味の確認**：最終MP4の各説明区間を動画または連続フレームで確認し、
何がどう動いて、どの仕組みを伝えたかを `motion-review.json` に記録する。
対象の変化が説明を担っていることを確認する。同じ最終ファイルのSHA-256を記録して再検査する。

```bash
python3 /path/to/science-explainer/scripts/audit_motion.py \
  outputs/final.mp4 --plan motion-plan.json --review motion-review.json \
  --output outputs/motion-audit.json
```

- A・Bともに合格して初めてアニメーションとして完了。修正したら再レンダー・再検査する。
- ffprobe、全編デコード、音量、字幕範囲、音声切れの検査も行う。
- 通常の学習用保持を壊すために動きを足さない。数値基準は制作上の検出用であり、視聴維持率の実証済み法則ではない。
- フレーム確認と全編の聴取、機械的な変化と意味のある動作を区別して報告する。

## 5. 保存と受け渡し

台本、出典、plan、動作計画・レビュー、コード、検証結果、必要な完成ファイルを作業ブランチにコミットしてpushする。
GitHubの確定URLからMP4を再取得してハッシュを照合し、ダウンロード用HTTPSリンクを渡す。
クラウドの `/workspace/...` だけを受け渡しリンクにしない。既存の変更を消さず、明示的依頼なしにworktreeを作らない。
